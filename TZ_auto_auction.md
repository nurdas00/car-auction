# ТЗ: Веб-сервис аукциона автомобилей (C2C)

## Context

Пользователь хочет запустить веб-сервис аукциона автомобилей. Проект создаётся с нуля, поэтому задача на этом шаге — подготовить техническое задание, которое дальше будет служить основой для разработки.

По ответам пользователя:
- **Тип аукциона:** C2C — частные продавцы выставляют б/у авто, частные покупатели делают ставки. Площадка выступает посредником и зарабатывает комиссию (модель как у Авито-аукциона / Copart, но без дилерского опта).
- **Объём первой версии:** минимальный MVP — регистрация, создание лота, ставки в реальном времени, завершение аукциона, базовые уведомления. Без встроенной оплаты и логистики на этом этапе.
- **Монетизация:** не зафиксирована — ниже даны варианты, решение принимается после MVP или как часть бизнес-валидации.
- **Технологии:** предложен конкретный стек с обоснованием.

---

## 1. Цель проекта

Создать веб-платформу, где частные владельцы автомобилей могут выставить машину на аукцион, а покупатели — соревноваться ставками в реальном времени за ограниченный срок, с прозрачным и честным завершением торгов.

## 2. Целевая аудитория

- **Продавцы:** частные лица, продающие личный автомобиль.
- **Покупатели:** частные лица, ищущие авто по рыночной цене через торги (потенциально ниже цены фиксированных объявлений).
- **Регион запуска:** Кыргызстан. Язык интерфейса — русский (основной деловой язык в стране), с заделом на киргизскую локализацию во второй версии.
- **Валюта:** ставки и цены хранятся и сравниваются только в сомах (KGS) — это единственная "валюта истины" для аукциона, иначе при разных валютах ставок невозможно однозначно определить, чья ставка выше, при скачках курса. Эквивалент в USD показывается рядом как справочный (не для ставок), пересчитывается по курсу НБКР (обновление — раз в сутки, см. раздел 5).

## 3. Роли пользователей

| Роль | Возможности |
|---|---|
| Гость | Просмотр списка лотов и карточки лота без возможности ставить |
| Покупатель | Регистрация, участие в торгах, избранное, история ставок |
| Продавец | Создание лота, управление своими лотами, просмотр ставок по своему лоту |
| Админ/модератор | Модерация лотов перед публикацией, блокировка пользователей, разрешение споров, снятие лота с торгов |

Один пользователь может быть и продавцом, и покупателем (единый аккаунт).

## 4. Функциональные требования — MVP

### 4.1 Аккаунты
- Регистрация/вход по email + пароль (хэширование, подтверждение email). На старте этого достаточно — телефон собирается в профиле, но не верифицируется.
- Восстановление пароля.
- Базовый профиль: имя, телефон, город, аватар.
- У пользователя хранится поле `verification_level` (`email` → `identity`), чтобы дальше можно было ужесточать требования без переделки модели данных.
- (v2, вне MVP) OAuth (Google), верификация телефона по SMS — если практика покажет проблему с ботами/мультиаккаунтами.
- (Этап 5, перед финальным релизом) полная верификация личности (KYC) — см. раздел 9.

### 4.2 Создание лота (продавец)
- Форма объявления: марка, модель, год, пробег, VIN (опционально), состояние, фото (до N штук), описание, город.
- Параметры аукциона: стартовая цена и шаг ставки задаются в сомах (KGS) — это единственные значения, участвующие в логике торгов; дата/время старта, длительность торгов, (опционально) резервная цена (reserve price) — скрытая минимальная цена продажи, тоже в сомах. Интерфейс дополнительно показывает текущую цену в USD по курсу НБКР — только для удобства восприятия, в сравнение ставок не участвует.
- Модерация: лот публикуется только после проверки админом (защита от мусора/мошенничества на старте).
- Статусы лота: черновик → на модерации → активен → завершён (продан/не продан) → отменён.

### 4.3 Аукционный движок (ядро системы)
- Торги в реальном времени: ставка одного участника немедленно видна всем остальным (WebSocket).
- Правила ставок: каждая новая ставка выше текущей минимум на шаг; нельзя перебить самого себя подряд (конфигурируемо).
- Таймер обратного отсчёта до конца торгов.
- **Anti-sniping**: если ставка сделана в последние N секунд (напр. 30–60 сек), время торгов автоматически продлевается на фиксированный интервал — защита от перехвата лота в последнюю секунду.
- Reserve price: если финальная ставка ниже резервной цены — лот помечается как «не продан», продавец решает вопрос вне платформы на этом этапе MVP.
- Запрет ставок для продавца на собственный лот.
- История ставок по лоту видна участникам (минимум: сумма и время, без раскрытия личных данных других участников до завершения).

### 4.4 Поиск и просмотр
- Каталог активных лотов с фильтрами: марка, модель, год, цена, город, статус.
- Карточка лота: фото, характеристики, текущая ставка, таймер, кнопка «Сделать ставку».
- Избранное / подписка на лот.

### 4.5 Завершение аукциона и уведомления
- Автоматическое завершение по таймеру, определение победителя (наивысшая ставка ≥ резервной цены).
- Уведомления (email, в будущем — push): о перебитой ставке, о скором окончании торгов, о результате аукциона (победа/проигрыш продавцу и покупателям).
- После завершения — обмен контактами между продавцом и победителем для оффлайн-оформления сделки (оплата и передача авто вне платформы на этапе MVP).

### 4.6 Админка
- Список лотов на модерации, одобрение/отклонение с причиной.
- Блокировка пользователей, снятие лота с публикации.
- Базовая статистика: количество лотов, активных торгов, завершённых сделок.

### Вне рамок MVP (явно не делаем сейчас)
- Встроенные платежи, escrow, депозиты за участие в торгах.
- Проверка VIN/истории авто через внешние базы.
- Логистика/доставка автомобиля.
- Рейтинги и отзывы о пользователях.
- Мобильное приложение (только responsive web).
- Мультивалютность/мультиязычность.

## 5. Нефункциональные требования

- **Real-time:** задержка отображения новой ставки у всех зрителей лота — не более 1–2 секунд.
- **Консистентность ставок:** при гонке одновременных ставок сервер должен атомарно определять, какая ставка принята первой (избегать race condition на уровне БД/бэкенда).
- **Безопасность:** защита от CSRF/XSS, rate-limiting на ставки (защита от скриптового перебития), валидация прав доступа (продавец не видит возможности ставить на свой лот и т.п.).
- **Масштабируемость:** архитектура должна переживать всплеск нагрузки в последние секунды популярного лота (много одновременных ставок).
- **Доступность:** целевой SLA для MVP — "best effort", без требования 99.9% (это решается на следующих этапах роста).
- **Логирование и аудит:** вся история ставок хранится неизменно (append-only) для разрешения споров.
- **Курс валют:** USD-эквивалент цены подтягивается раз в сутки с курса НБКР (nbkr.kg) и кэшируется — внешний сервис не дёргается на каждый просмотр страницы; при недоступности источника показывается последний сохранённый курс с отметкой времени.

## 6. Варианты монетизации (к решению)

Поскольку модель не выбрана, в ТЗ фиксируются варианты, совместимые с архитектурой C2C-аукциона — решение не блокирует разработку MVP, так как оно влияет в основном на биллинг-слой, который в MVP отсутствует:

1. **Комиссия с продажи** (% от финальной цены, с продавца и/или покупателя — buyer's premium). Самый распространённый вариант для аукционов, не требует платы до результата.
2. **Платное размещение лота** — фиксированная плата за публикацию объявления, независимо от продажи.
3. **Подписка** — для активных продавцов/дилеров (менее релевантно для чистого C2C, но можно добавить позже).

Рекомендация: на MVP не внедрять биллинг вообще (сделки оформляются вне платформы), а начать с варианта (1) после валидации спроса — комиссию удобнее добавить постфактум, когда есть объём сделок для измерения.

## 7. Технологический стек (предложение)

Критерий выбора: реалтайм из коробки, высокая устойчивость аукционного движка к конкурентной нагрузке, простой деплой.

- **Frontend:** React + TypeScript, Next.js (SSR для SEO каталога лотов + CSR для live-торгов). Остаётся на TypeScript независимо от выбора бэкенда.
- **Backend:** Go — модель "комната лота = независимый поток ставок" естественно ложится на goroutines/channels; каждый лот может обслуживаться отдельной goroutine-"комнатой", которая серилизует входящие ставки без явных блокировок БД. HTTP/REST: `chi` или `net/http` из стандартной библиотеки (достаточно для MVP, без лишнего фреймворка).
- **Real-time:** WebSocket через `nhooyr.io/websocket` или `gorilla/websocket`; Redis Pub/Sub — шина для синхронизации ставок между несколькими инстансами бэкенда (если держим больше одного процесса).
- **БД:** PostgreSQL, доступ через `sqlc` (типобезопасный SQL без тяжёлого ORM) или GORM, если важнее скорость написания кода. Транзакции обязательны для фиксации ставки (сравнение с текущим максимумом + запись — одна атомарная операция).
- **Кэш/блокировки:** Redis — для хранения "горячей" цены/таймера лота и координации между инстансами; в пределах одного инстанса конкурентность ставок по лоту проще держать на канале goroutine-комнаты, а не на Redis-локах.
- **Файлы (фото авто):** S3-совместимое хранилище (AWS S3 / Cloudflare R2) + CDN — без изменений.
- **Email:** транзакционный провайдер (SendGrid / Resend) — без изменений.
- **Хостинг:** Go-бэкенд собирается в один статический бинарник → Docker-образ получается минимальным; деплой на любом облаке с managed Postgres/Redis.
- **Аутентификация:** email/password, хэширование `bcrypt`/`argon2`, сессии или JWT через стандартные Go-библиотеки (`golang-jwt`) — без внешнего IdP на старте.

## 8. Высокоуровневая архитектура

```
[Browser] --HTTP--> [Next.js app] --REST--> [Go API сервер] --> [PostgreSQL]
   |                                              |
   +-----------------WebSocket------------>[Auction Room: goroutine на лот] <--Pub/Sub--> [Redis]
```

- REST API (Go) — создание лотов, аутентификация, профиль, каталог.
- Auction Room — на каждый активный лот запускается своя goroutine с каналом входящих ставок; она последовательно обрабатывает ставки (нет гонки данных), обновляет цену/таймер, применяет anti-snipe и транслирует подтверждённую ставку всем WebSocket-подписчикам лота.
- Redis — синхронизация состояния лота между инстансами (если бэкенд масштабируется горизонтально) и источник для Pub/Sub между процессами; Postgres — источник истины для истории ставок и финального результата.

## 9. Этапы разработки

1. **Этап 0 — фундамент:** аутентификация, профиль, схема БД, базовый CRUD лотов (без торгов).
2. **Этап 1 — аукционный движок:** WebSocket-комнаты, логика ставок, anti-snipe, завершение по таймеру.
3. **Этап 2 — каталог и UX:** поиск/фильтры, карточка лота, избранное.
4. **Этап 3 — модерация и уведомления:** админка, email-уведомления.
5. **Этап 4 — полировка MVP:** нагрузочное тестирование аукционного движка, защита от конкурентных ставок, базовая аналитика.
6. **Этап 5 — верификация личности (KYC), перед финальным релизом (вне MVP):** интеграция со сторонним KYC-провайдером (напр. Sumsub), обязательна для `verification_level = identity`; требуется перед созданием лота и/или перед участием в торгах выше определённой суммы — порог уточняется исходя из юридических требований на момент релиза.

## 10. Критерии приёмки MVP

- Пользователь может зарегистрироваться, создать лот, пройти модерацию и опубликовать его.
- Несколько пользователей одновременно видят одинаковую текущую цену и таймер лота с задержкой < 2 сек.
- Ставка ниже текущей/шага отклоняется с понятной ошибкой.
- Ставка в последние секунды продлевает торги согласно правилу anti-snipe.
- По истечении времени система однозначно определяет победителя или помечает лот как непроданный (reserve не достигнут).
- Продавец и победитель получают уведомление с контактами друг друга после завершения.
